先抓主轴：Multica 不是单个 Web App，而是一套把 Agent 纳入工作流的分布式系统

如果只记一句话：Multica 把 AI agent 变成工作区里的正式成员。Issue、评论、Inbox、项目、技能、Autopilot 都围绕这个前提组织，而不是围绕“临时调用一次模型”组织。

Execution Plane

Daemon + AI Coding Tool

  • daemon 跑在用户机器上，发现本地可用的 AI 编程工具
  • AI coding tool 真正读代码、写代码、跑命令、发评论
  • API key、代码目录、工具授权尽量留在本地
  • runtime 是产品里的“可用执行槽位”
最重要的产品边界： Multica 的 server 管任务与协作状态，agent 的执行发生在 runtime 上。这也是它和传统工单系统、以及单次对话式 AI 工具的根本区别。

Multica 术语表

仓库有长版的 docs/product-overview.md，但真正指导代码讨论的应该是短而硬的词汇表。这里按最新 CONTEXT.md 重排，优先收紧最容易被混用的概念。

Workspace

一切资源的顶层容器。Issue、Agent、Skill、Project、Member 都在这个边界内隔离。

Avoid: team, org, tenant
Member

用户在某个 workspace 里的身份与角色，而不是全局账号本身。

Avoid: user, teammate
Agent

可被分配工作的 AI 成员，会在工作区里发评论、接任务、参与协作，不只是一次性模型调用。

Avoid: bot, model
Squad

由 agent 领导的路由组。工作可以先分给 squad，再由 leader 决定谁真正接手。

Avoid: team, queue
Issue

Multica 的核心工作对象。人和 agent 都围绕它协作。

Avoid: task, ticket
Project

Issue 的高层组织容器，用于聚合多个工作项的共同目标。

Avoid: epic, milestone
Project Resource

挂在项目上的仓库、目录或其他上下文引用，让 agent 在项目内执行工作时拿到额外背景。

Avoid: attachment, runtime
Chat Session

Issue 外的持久一对一对话，和 Issue 线程不是一回事。

Avoid: issue thread, task
Inbox Item

围绕 issue 活动形成的个人 attention 条目，不等于所有系统状态变化都会进这里。

Avoid: generic alert, message
Task

一次 agent 执行记录。它是“agent 开跑的那次实例”，不是长期存在的工作项。

Avoid: issue, job
Daemon

本地后台进程，负责注册 runtime、领任务、启动 AI coding tool、回传结果。

Avoid: agent, runtime
AI Coding Tool

真正执行工作的本地 CLI，例如 Claude Code、Codex。它不是 runtime，也不是 agent 本身。

Avoid: model, provider
Runtime

Agent 真正执行任务的槽位。今天它是 workspace 内 “daemon × 一个 AI coding tool” 的组合。

Avoid: server, machine
Skill

给 agent 的可复用知识包，用来沉淀做事方法，不等于一次性 prompt。

Avoid: prompt, template
Workspace Context

工作区范围的统一指令，会影响该 workspace 里 agent 的工作方式。

Avoid: global prompt, org policy
Autopilot

按时间或 webhook 触发的自动化入口，会为 agent 创建或派发工作。

Avoid: cron job, bot rule

Monorepo 的真实分层：不是“前后端”两层，而是“控制面 + 客户端 + 共享业务层”

这个仓库最值得记住的不是目录名，而是边界：packages/core 负责业务逻辑，packages/ui 负责纯 UI， packages/views 负责共享业务页面；Web 与 Desktop 共享这三层，Mobile 只共享类型和纯函数。

server/ 控制面

Go 后端负责数据模型、权限、实时事件、任务队列、CLI/daemon 命令入口。它定义“产品怎样运作”。

apps/web / apps/desktop

两端共享大多数业务视图，只在平台 API、壳层能力、路由接线处各自分化。

apps/mobile

移动端是独立客户端，不直接复用 Web/Desktop 的业务层实现，只共享 @multica/core 的类型和少量纯函数。

packages/core

查询、变更、缓存键、Zustand store、路径与平台无关逻辑。它是“产品行为”的主要共享层。

packages/ui / packages/views

ui 只放原子组件；views 组织页面与业务组件，但不依赖 Next.js 或 React Router。

apps/docs

文档站已经拥有很完整的产品说明体系，这次 HTML 更像一份“压缩版总览图”，不是从零写新知识。

读代码的一个高收益顺序： 先从 docs/product-overview.md 和 docs 站定义产品对象，再去 packages/core/<domain> 看状态与 API，再看 packages/views/<domain> 或各端入口如何呈现。这样不会一上来就迷失在实现细节里。

一条工作如何穿过系统：从 Issue 指派到 Agent 回报

这个流程最能说明 Multica 的产品心智模型：Issue 是工作单，Task 是执行记录，Runtime 是执行地点，Comment / Timeline 是稳定协作回路，Inbox 只覆盖其中一部分 attention 信号。

Step 01

创建或更新 Issue

用户在 Web / Desktop / Mobile 上创建 issue，或把已有 issue 分配给 agent。

Step 02

后端入队 Task

server 改写 issue assignee，并创建一条 agent task，状态先进入 queued。

Step 03

Daemon 认领执行

daemon 轮询到这条任务，在本地 runtime 上启动对应 AI coding tool，任务变成 running。

Step 04

Agent 本地工作

AI coding tool 读仓库、改代码、跑命令、生成评论或更新状态；Skill 和 workspace context 在这里生效。

Step 05

结果回传 server

完成、失败、评论、状态变化都回传给 Go 后端，落库并写入活动流。

Step 06

实时同步给所有客户端

WebSocket 把变化推到 Web / Desktop / Mobile；Timeline、聊天窗口与 issue 状态变化会稳定体现执行结果，Inbox 只覆盖部分需要 attention 的场景。

失败语义要单独记： 不是每一种失败都会进入 Inbox。按当前实际行为，Autopilot 失败更可靠的信号是 run history 与关联 issue 的状态变化；你这边确认的现象是没有失败通知，只是 issue 状态转到 block。 所以在产品分析里，不要把 Inbox 当成所有执行失败的统一出口。

如果你是新协作者，应该怎样读这套仓库

这份 HTML 不是替代源码，而是提供一条进入源码的路径。下面这 4 步最省时间。

01. 先看产品词

读 CONTEXT.md 与 docs/product-overview.md，先区分 Issue、Task、Runtime、Daemon、Skill 的边界。

02. 再看共享业务层

从 packages/core 进入目标领域，理解查询、变更、缓存键和 store 的结构。

03. 再看共享视图或端入口

Web/Desktop 优先看 packages/views；移动端优先看 apps/mobile 自己的实现。

04. 最后回到 server

需要确认事实来源、权限或任务生命周期时，再下钻 server/internal/handler 与 server/internal/service。

一句话总结

Multica 的产品核心不是“聊天”也不是“工单”，而是把 agent 变成工作区里的正式执行者，并把执行留在用户自己的 runtime 上。 这套代码库的正确阅读方式是从产品对象与术语出发，顺着共享业务层找到各客户端表现.
